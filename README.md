# FPD-Link(OpenLDI, "LVDS") display controller for Gowin FPGAs

This project mostly targets Tang nano 9k board.
It should work on any other boards, but I can't guarantee that other chips will support primitives used here in the same way.

My config is: Samsung LTN156AT35 panel(1366x768p, 60hz, single-link 6-bit panel); 4x 220ohm resistors per pair<br>


**WARNING! Resistor network is NECESSARY if your FPGA board does not route out 2.5V-powered IOs which can do true LVDS. Skipping resistor network may permanently damage your panel!**<br>

**BE ATTENTIVE! Most laptop panels from ~2013 and later are eDP, not LVDS. Check panel datasheet and pins. The connectors can be similar. eDP is much more complex protocol(pretty much usual DisplayPort), and to drive that you need much more advanced FPGA and complex design, or just use adapter board/IC which will do all dirty job for you.**
<p>Explanation: These or similar laptop panels require LVDS signal: diff pair centered around 1.25V, with 250-350mV differential swing. Gowin FPGAs do NOT support such output mode on banks powered from 3v3. For such output mode(LVDS25) the bank must be powered from 2.5V, and this is very rare on dev boards. To get this on 3v3 banks, resistor network is required. FPGA's job is to toggle 2 pins so they are always opposites(HIGH - LOW or LOW - HIGH). Gowin FPGAs can do this better if not using generic LVCMOS33 IOs and inverting in fabric, but using special LVCMOS33D IO mode. This also requires ELVDS_OBUF primitives, which take usual on/off signal and convert it to opposite signals to output. And resistors try to take usual 0-3v3 opposite signals into LVDS-like signal. True LVDS works differently, but resistors mimic this good enough. Ignoring resistors will lead to 0-3v3 signals reaching panel TCON's sensitive receivers, which may lead to permanent damage, or just something not working. Panel typically has internal 100ohm termination(read, resistors between P and N) which will soften wrong levels, but you really shouldn't gamble if you care about the panel, this is far out of spec.</p>
<p>FPD-Link, OpenLDI or just LVDS(this name relates to electrical level, not the protocol, but it is a popular way to call these panels) needs serial signal - 7 bits per pixel clock default. 3 diff pairs are data, and 1 is clock(for single-link panels, again). Clock lane must be treated the same as data lanes, but having hardcoded constant data(1100011), instead of pixel and sync data on data lanes. In Gowin FPGAs, there is a special primitive for hardware 7:1 gearbox, called "OVIDEO". It takes 7 bits of data, pixel("parallel") slow clock and fast("serial") clock, which must be 3.5x of pixel clock. It is 3.5x and not 7x because the gearbox works is DDR. !!Important - these clocks must be phase-aligned(generated from one PLL)!! Gowin CLKDIV has 3.5 division mode, so the simplest and pretty much the only way to generate clocks is to configure PLL for serial clock, and divide it.</p>
<p>When clocks and PHY level(resistors, IO pins and serializers) are done, we need to generate some picture! But pushing out RGB bits is not enough. TGEN must generate vsync, hsync, de(display enable) signals for the panel's IC to keep track of pixels and frames, and it will help user logic to keep track of pixels too. For most panels, vsync and hsync signals are not important, they need only DE. In the code, only DE is wired. Also, as said, TGEN keeps track of pixel coordinates. In fpdlink.sv you can comment and uncomment several lines to make pixel coordinates lag behind for 1 pixel clock cycle, so user logic has one full cycle to prepare pixel color. Without this, all logic choosing pixel color must fit into ~70mhz datapath, which is tight for anything complex. Check timing reports!</p>
<p>After TGEN, we finally have pixel color input and pixel coordinates. Module tells pixel coordinates, user logic tells color of that pixel, its as simple as that.</p>
<p>This is mostly code I wrote for myself, it has almost no parameters, and squeezed into a single file for convenient use. You may edit timings, PLL settings(for different clock, which is needed if you change timings), tgen pixel coordinates lag. Check everything carefully, be aware that if there are some parameters, it doesn't mean that changing them configures everything perfectly.
</p><p>About signal integrity. Diff pairs run at really fast clock(486Mbps in this case) which is significant for these FPGAs. Display cable is wrapped in conductive tape and diff pairs are twisted for a reason. Try to not untwist pairs too much, keep everything tidy, and be really careful with resistors. Its the biggest point of failure, and this circuit already works at its limits. Keep the legs short, close to PCB pads, wires as similar in length as possible(inter-pair and intra-pair skew is already a concern at such speeds). Overall, if everything is very tidy, but nothing works, its not the issue. But if the controller can sync, some image appears, but it flickers, loses sync - try to minimize signal integrity problems. Also running PWM or other digital interfaces(PWM signal for backlight, EDID I2C for example) close to diff pairs can degrade signal. Diff pairs must cancel the noise, but it can still be a reason for poor signal.</p>
